# Book repository format, version 3

A book in this format is a git repository of plain Markdown and YAML files. You can read and edit it on github.com or in any text editor; the app is a convenience, not a requirement. This document is the contract that the app, the validator, the diagrams and the exporters all follow.

Every book is of a **kind** ([D14](https://github.com/heffrey78/writer/issues/10), [D15](https://github.com/heffrey78/writer/issues/11)): a novel, and others to come. Its kind gives it its levels of sections, its writing unit (the novel's scene), its folders, its built-in entry types, its statuses and the kinds of its issues (see *Kinds*). Format 3 names the kind in `book.yaml`. Formats 1 and 2 were gh-writer's, for novels only: a book with `novel.yaml` is a novel, read and edited as it is, without migrating it ([#2](https://github.com/heffrey78/writer/issues/2)). Most of this document describes the Novel kind, the only one so far; what other kinds do differently is in *Kinds*.

Design rules (from decisions [D1](https://github.com/heffrey78/gh-writer/issues/21) and [D3](https://github.com/heffrey78/gh-writer/issues/23)):

- **One home per fact.** Story facts live in these files. Work and discussion (plot holes, research, revision notes) live in GitHub Issues.
- **References use IDs, never names or paths.** Renaming or moving anything never breaks a link.
- **Order lives in order files.** Moving a scene edits two order files and moves one file; no references change.

## Layout

```
book.yaml                           # the book's settings and kind, entity types, relationship types
                                    #   (novel.yaml in formats 1 and 2)
dictionary.txt                      # optional: words the spell checker accepts
compile.yaml                        # optional: how the manuscript is compiled (presets)
manuscript/
  _order.yaml                       # top-level order: parts, or chapters if the book has no parts
  01-act-one/                       # a part (optional level)
    _part.yaml
    01-arrival/                     # a chapter
      _chapter.yaml
      01-the-station.md             # a scene: front matter + prose
      02-the-bridge.md
bible/
  characters/ada.md                 # one file per entity: front matter + free-form notes
  locations/
  plotlines/
  themes/
  <custom type folder>/
  relationships.yaml                # every relationship between entities, once
  events/                           # off-page story events, one file each
    the-flood-of-09.md
notes/                              # optional: the writer's notes, one file each (not story facts)
  what-if-ben-never-sold.md
diagrams/
  layouts.yaml                      # hand-arranged node positions
images/                             # optional: pictures of bible entries, the cover and the prose
  ada-varn.jpg
  cover.jpg
.github/
  gh-writer/validate.mjs            # vendored tools (see "Upgrading a novel's tools")
  gh-writer/snapshots.mjs
  gh-writer/compile.mjs
  gh-writer/fonts/                  # the compiler's type, Liberation Serif (SIL OFL)
  workflows/validate.yml
  workflows/diagrams.yml
  workflows/compile.yml
```

Books with parts put part folders under `manuscript/`. Books without parts put chapter folders directly under `manuscript/`. A book uses one or the other, not both.

Folder and file names are for humans. The `NN-` number prefixes are cosmetic and the app regenerates them from the order files. If they disagree with the order files, the order files win and the validator warns (`W_FILENAME_ORDER`).

## IDs

Every record has an immutable ID: a type prefix, an underscore, and six characters from the lowercase [Crockford base32](https://www.crockford.com/base32.html) alphabet (`0-9 a-h j k m n p-t v-z`; no `i l o u`).

```
char_7f3k2q    sc_0d9wm4    rel_q2m9xa
```

| Prefix | Record | Prefix | Record |
|---|---|---|---|
| `nv` | the novel | `char` | character |
| `pt` | part | `loc` | location |
| `ch` | chapter | `plot` | plotline |
| `sc` | scene | `theme` | theme |
| `rel` | relationship | `evt` | event |
| `note` | note | | |

The book's own ID has its kind's prefix (`nv` for a novel, before and after a move to format 3: IDs never change). Custom entity types declare their own prefix (see the manifest). IDs are random so that books can be combined into a series later without collisions. Generate one with `writer new-id <prefix>`.

## The manifest: `book.yaml`

```yaml
schema_version: 3
kind: novel                  # what kind of book this is (see Kinds)
id: nv_4k8h2c
title: The Bridge at Varn
author: J. Wikstrom
cover: images/cover.jpg      # optional: the book's cover
language: en                 # optional (BCP 47): the book's language, for e-books; default en
target:                      # optional
  words: 90000
  date: 2027-06-30
  daily: 500                 # words a day aimed for
entity_types:                # optional: custom types, added to the built-in four
  - key: artifact
    prefix: art
    folder: artifacts
    label: Artifact
    color: "8c564b"          # optional, GitHub label colour (hex, no #)
relationship_types:
  - key: sibling
    label: Sibling
    symmetric: true
  - key: mentor
    label: Mentor of
    inverse_label: Mentee of
    from_types: [character]
    to_types: [character]
calendar:                    # optional
  start: 2024-03-01          # what "day 1" means for relative times
plotline_gap:                # optional: when a plotline's silence counts as a gap
  scenes: 3                  # or words: 5000
sidebar:                     # optional (format 3): the writer's arrangement of the app's sidebar
  groups:
    plan: [notes, outline]   # a group's pages, in order, by key
  hidden: [compare]
```

| Field | Required | Notes |
|---|---|---|
| `schema_version` | yes | Integer. This document describes `3`; see *Versioning* for what changed before it. |
| `kind` | yes (format 3) | The kind of book, by its key: `novel`. A kind this copy of the app or validator doesn't ship is `E_UNKNOWN_KIND`, and nothing else is read. |
| `id` | yes | The book's ID, with its kind's prefix: `nv_` for a novel. |
| `title` | yes | |
| `author` | no | |
| `cover` | no | The book's cover: a repository path to a JPEG or PNG image. It's shown on the app's library shelf, is the EPUB's cover and the PDF's first page; Word manuscripts go out without one. The app saves it as `images/cover.jpg` (or `.png`), 1600 × 2560 px. |
| `target.words`, `target.date`, `target.daily` | no | Positive integer; ISO date; positive integer. The length to reach, by when, and the words a day aimed for (words added, not net). |
| `entity_types` | no | Custom bible entity types. `key` (lowercase), `prefix` (2–8 lowercase letters, not reserved), `folder` (under `bible/`; not `events`, which holds off-page events), optional `label` and `color`. |
| `relationship_types` | no | `key`, optional `label`, `symmetric` (default `false`), `inverse_label`, `from_types`, `to_types` (entity type keys), and `style`: how diagrams draw it, `color` (`series-1` to `series-8`: the slots of the app's chart palette, blue, orange, aqua, yellow, magenta, green, violet and red, each with a light and a dark step) and `line` (`solid`, `dashed` or `dotted`). The older names `accent`, `warn`, `ok`, `danger`, `ink` and `muted` still read, as `series-1`, `series-4`, `series-6`, `series-8`, `series-7` and `series-3`. Without a colour, a type takes the slot of its place in the list; the app saves one when it makes a type. |
| `calendar.start` | no | ISO date that relative day 1 maps to. |
| `sidebar` | no | Format 3 only: how the writer arranged the app's sidebar. `groups` maps each of the kind's sidebar groups, by key (a novel's `plan` and `revise`, a journal's `look-back` and `people-and-places`), to its pages in order; `hidden` lists pages not shown. `bar` lists the pages in a phone's bottom bar after where the book opens, in order (three are shown, with More after them; #100). Pages are named by key: `outline`, `story-map`, `relationships`, `notes`, `progress`, `index`, `compare`, `issues`, or a module's page (`calendar`, `read`). A page named nowhere is where the kind puts it. A group or page the kind doesn't have is `W_SIDEBAR_UNKNOWN`. |
| `plotline_gap` | no | `{ scenes: N }` or `{ words: N }` (whole numbers, 0 or more): a plotline unmentioned for more than this, between two of its beats or after its last, is shown as a gap in the plotline swimlanes. Default `{ scenes: 3 }`. |

Built-in entity types are always present: `character` (`char`, `bible/characters`), `location` (`loc`, `bible/locations`), `plotline` (`plot`, `bible/plotlines`), `theme` (`theme`, `bible/themes`).

A novel in format 1 or 2 keeps the same fields in `novel.yaml`, without `kind`, and with `schema_version` 1 or 2. Tools read it as it is. `writer migrate` (or the app, when the writer asks: *Move this book to the new format…*) moves it to format 3 in one commit: `novel.yaml` becomes `book.yaml`, with `schema_version: 3` and `kind: novel` after it, every other byte as it was. A book has one manifest: with both, `book.yaml` is the one read.

## Kinds

A kind of book is shipped with the app, as data its tools read. It declares:

|---|---|---|---|---|
| Levels of sections, outermost first: each a key, a label, an ID prefix, the key its sections are listed under (`list`), whether a book may go without it (`optional`, outer levels only) and whether its sections must have a title (`titled`) | `part` (Part, `pt`, `parts`, optional, titled), then `chapter` (Chapter, `ch`, `chapters`) | `year` (Year, `yr`, `years`, optional, titled), then `month` (Month, `mon`, `months`, titled) | `arc` (Arc, `arc`, `arcs`, titled) | `part` (Part, `pt`, `parts`, optional, titled), then `chapter` (Chapter, `ch`, `chapters`, titled) |

| Built-in entry types (a module the kind uses may add its own), each saying where it matters whether its entries are people or places | character (people), location (places), theme, and plotline from the plotlines module | person (people; "People"), place (places), event, value | npc (people; "NPCs"), pc (people; "Player characters", folder `player-characters`), location (places), faction, item, quest | source, person (people; "People"), concept, claim |
| Statuses of a piece, in order, the first a new one's | idea, outlined, drafted, revised, final | draft, kept | planned, prepped, played | outline, draft, revised, checked |
| A piece's fields beyond `id`, `title`, `synopsis`, `status` and `tags` (every kind's): each a key, a label and a type (one entry of a type; entries of a type, each a plain ID or `{ id, … }` carrying the field's item properties; entries of the book's own types; story time with its duration), in the order the piece's card shows them; a module the kind uses adds its own (the Novel's point-of-view module adds `pov`, its plotlines module `plotlines`, its story-time module `when`) | `pov`, `locations`, `characters`, `when` with `duration`, `plotlines` (weight, beat), `entities`, `themes` (strength, note): see *Scenes* | `when` (its date, from the story-time module), `people`, `places`, `events`, `values` (strength) | `when`, `party` (player characters), `npcs`, `locations`, `factions`, `items`, `quests` (threads through the sessions), `entities` | `sources`, `people`, `concepts` (threads through the book), `claims`, `entities` |
| Kinds of issue (labels `kind/<key>`) | plot hole, continuity, research, idea, revision | follow up, fact | loose end, ruling, idea | fact check, citation needed, research, idea |

| The Markdown a new piece starts with (`piece.template`), as the editor writes it, from the tree, the palette or anywhere else a piece is made; without it, a new piece is empty | none | none | a session's prep: `##` headings Strong start, Scenes, Secrets and clues, NPCs, Locations, Treasure, then At the table | none |

It's pinned there, taking the pin from the note pinned before, with the caret in it | none | none | *Note from the table*, “At the table: Session 3” | none |
| Whether a piece's title is a heading in the compiled book (`piece.headed`), beneath its chapter's; without it, pieces are set apart by the preset's break and their titles left out | no | no | no | yes: each section is headed by its title |

| Modules | point-of-view, plotlines, presence, off-page-events, story-time, drafting-board, manuscript-format | presence, story-time, daily | presence, story-time | presence, citations |

The structure follows from the levels, for any kind. The content folder's `_order.yaml` lists the top sections under their level's `list`: a book starts at one of its kind's levels (an optional one, or the first that isn't) and has every level after it. A section is a folder holding `_<level>.yaml`: its `id`, `title` (required where the level is `titled`) and `synopsis`, and its children in order under the next level's `list`, or at the innermost level the pieces' (the Novel's `scenes`). Pieces are Markdown files in sections of the innermost level. A novel in parts is `parts` → `_part.yaml` (`chapters`) → `_chapter.yaml` (`scenes`) → scenes, as *Order files* describes.

## Order files

`manuscript/_order.yaml` lists exactly one of:

```yaml
parts: [pt_1a2b3c, pt_4d5e6f]
```
```yaml
chapters: [ch_1a2b3c, ch_4d5e6f]
```

`_part.yaml`, in each part folder:

```yaml
id: pt_1a2b3c
title: Act One
synopsis: Ada arrives in Varn.   # optional
chapters: [ch_7g8h9j, ch_0k1m2n]
```

`_chapter.yaml`, in each chapter folder:

```yaml
id: ch_7g8h9j
title: Arrival                   # optional; many chapters are untitled
synopsis: ...                    # optional
scenes: [sc_0d9wm4, sc_5p6q7r]
```

Each order list must name every child in that folder exactly once and nothing else.

## Scenes

A scene is a Markdown file inside a chapter folder: YAML front matter between `---` lines, then prose.

```markdown
---
id: sc_0d9wm4
title: The Bridge
synopsis: Ada learns Ben sold the plans.
status: drafted
pov: char_7f3k2q
characters: [char_7f3k2q, char_b3n0vs]
locations: [loc_br1dg3]
entities: [art_p1an5x]             # entries of custom types (here, an artifact)
plotlines:
  - plot_h315tz                    # shorthand: a plain ID
  - id: plot_gr1efa
    weight: minor
    beat: First crack in the alliance
themes:
  - id: theme_trvst5
    strength: 3
when:
  day: 3
  time: "18:30"
duration: PT45M
tags: [rewrite-candidate]
---
The wind came off the river hard enough to lean on.

[Ada](#char_7f3k2q) saw him before he saw her.
```

| Field | Required | Notes |
|---|---|---|
| `id` | yes | `sc_` ID. |
| `title` | yes | |
| `synopsis` | no | One or two sentences, used on cards and outlines. |
| `status` | no | `idea` (default), `outlined`, `drafted`, `revised`, `final`. |
| `pov` | no | A character ID. |
| `characters` | no | Character IDs present in the scene. |
| `locations` | no | Location IDs. |
| `entities` | no | IDs of entries of custom types (see `entity_types`) present in the scene, in any order; each one's type is known from its prefix. The built-in types have their own fields above. |
| `plotlines` | no | Plotline IDs, or objects `{id, weight: major\|minor, beat}`. Default weight is `major`. |
| `themes` | no | Theme IDs, or objects `{id, strength: 1–3, note}`. |
| `when` | no | Story time: `{at: <ISO 8601 date or date-time>}` or `{day: <integer>, time: "HH:MM"}`. |
| `duration` | no | ISO 8601 duration, e.g. `PT45M`, `P2D`. |
| `tags` | no | Free-form strings. |

### Prose conventions

- **One paragraph per line**, with paragraphs separated by a blank line. Don't hard-wrap prose. That keeps git diffs and review comments to one paragraph each. For intentional line breaks such as verse or letters, end the line with a backslash (`\`) or two spaces.
- **Mentions** of bible entities and off-page events are ordinary Markdown links to their ID: `[Ada](#char_7f3k2q)`, `[the flood](#evt_9ab3kd)`. They render as harmless links on github.com, and exporters turn them into plain text.
- Scene breaks are implied between scene files. Don't add `***` separators between scenes.
- **A section break within a scene** is `***` on its own line.
- **Headings** `#`, `##` and `###` are the scene's own: a letter's date, a document's title, a day in a diary. The chapter's heading isn't written in the file; compile sets it, and sets the scene's headings beneath it. `####` and deeper read as `###`.
- **Lists**, bulleted (`-`) and numbered (`1.`), may nest. A numbered list keeps its first number. A list's numbers aren't words.
- **Tables** are GitHub's: a header row, an alignment row and rows of cells, each cell one line of text (emphasis, links and mentions included). There are no merged cells.
- **Pictures** stand on a line of their own: `![alt text](/images/valley.jpg "Caption")`. The path is written from the repository's root, so github.com shows the picture from any folder, and the file is in `images/`. The alt text describes the picture for those who can't see it. The caption is optional and is printed under the picture. Captions count as words; alt text doesn't.
- **Footnotes** are Markdown's: a reference `[^1]` where the note belongs, and its text beneath the prose, `[^1]: The note.`, with any further paragraphs of it indented four spaces. A file's labels are its own. The app numbers a new footnote one past the file's highest, and writes an empty one as `[^2]:`. In the EPUB and the PDF, a chapter's notes follow it, numbered from 1 in the order they're first referred to (in the EPUB, linked both ways); in the DOCX they're Word's own footnotes, at the foot of their page, which Word numbers through the book. A footnote's text counts as words; its reference doesn't.
- **Citations** (a kind with the citations module, the Non-fiction book's): a footnote cites a source by mentioning it, `[^1]: [Vegetable Mould](#src_d4rw1n), p. 258.` A source's details are its entry's fields: `author`, `year`, `publisher`, `place`, `url`. Compiled, a mention in a note whose words are the source's name or one of its aliases reads as its short form, the author's surname and the source's first alias (else its name): "Darwin, Vegetable Mould". The book ends with a bibliography of the sources its compiled sections draw on.
- Anything else Markdown can hold (code, HTML, footnotes, a picture within a line of text) is kept exactly as written, and compile leaves out what isn't text.

The app writes these the same way when you edit them: `-` bullets, `1.` numbering, aligned table columns and `#` headings. A scene you haven't edited is saved byte for byte, whatever its syntax.

## Bible entries

One Markdown file per entity in the folder for its type, such as `bible/characters/ada.md`. The file name is a slug and may change freely.

```markdown
---
id: char_7f3k2q
name: Ada Varn
aliases: [Ada, the Engineer]
summary: Bridge engineer who returns home to find the city sold out.
image: images/ada-varn.jpg
image_focus: [0.52, 0.3]
fields:
  age: 34
  eyes: grey
tags: [protagonist]
---
Free-form notes, backstory, voice samples...
```

| Field | Required | Notes |
|---|---|---|
| `id` | yes | Prefix must match the folder's entity type. |
| `name` | yes | Display name. |
| `aliases` | no | Other names the app recognises when suggesting mentions. |
| `summary` | no | Shown on hover cards. |
| `image` | no | A picture of the entry: a repository-relative path to an image. The app saves pictures in `images/`, named after the entry (`images/ada-varn.jpg`), resized on import: a portrait of 1200 × 1500 px for a character or an entry of another type, a wide picture of 1600 × 900 px for a location. JPEG, or PNG for an image with transparency. Pictures elsewhere in the repository (such as `bible/images/`) are fine too. |
| `image_focus` | no | Where small and differently shaped copies of the picture (cards, thumbnails) centre: `[x, y]`, each a fraction of the picture's width and height, from 0 to 1. Default the middle. |
| `fields` | no | Custom key/value pairs (string, number or boolean values). |
| `tags` | no | Free-form strings. |

## `bible/relationships.yaml`

Every relationship is recorded once, here.

```yaml
relationships:
  - id: rel_q2m9xa
    from: char_7f3k2q
    to: char_b3n0vs
    type: sibling
  - id: rel_x81cpz
    from: char_7f3k2q
    to: char_b3n0vs
    type: rival
    since: sc_0d9wm4
    note: After the bridge betrayal.
```

| Field | Required | Notes |
|---|---|---|
| `id` | yes | `rel_` ID. |
| `from`, `to` | yes | Bible entity IDs. For a `symmetric` type, the direction carries no meaning. |
| `type` | yes | A `relationship_types` key from `novel.yaml`. |
| `since` | no | Scene ID. The relationship holds **from this scene on** (inclusive). |
| `until` | no | Scene ID. The relationship holds **up to, but not including,** this scene. |
| `note` | no | |

A relationship applies at scene *S* when `since` is absent or at or before *S* in reading order, and `until` is absent or after *S*. To show a change, end one record with `until: sc_X` and start the next with `since: sc_X`.

## Off-page events: `bible/events/`

Off-page story events (backstory, things that happen between scenes) are placed on the timeline among the scenes. They're the off-page-events module's, which needs the story-time module: a book of a kind that doesn't list it (the Novel does) has none, and its tools don't read `bible/events/`. Each is one Markdown file in `bible/events/`, such as `bible/events/the-flood-of-09.md`: YAML front matter, then the event's note as prose, which may mention entries and other events. The file name is a slug and may change freely.

```markdown
---
id: evt_9ab3kd
title: The flood of '09
when: { at: 2009-11-02 }
duration: P3D
characters: [char_7f3k2q]
locations: [loc_br1dg3]
plotlines: [plot_h315tz]
scene: sc_0d9wm4
---
[Ada](#char_7f3k2q)'s father holds the seventh pier through the night.
```

| Field | Required | Notes |
|---|---|---|
| `id` | yes | `evt_` ID. |
| `title` | yes | |
| `when`, `duration` | no | As in scenes (see *Story time*). |
| `characters`, `locations`, `plotlines` | no | Character, location and plotline IDs, as in scenes. Plotlines here are plain IDs. |
| `scene` | no | The scene that dramatizes the event, when it has been written as one and kept. |

In format 1, events were a list in `bible/events.yaml`, each with a one-line `note`. Tools still read that file, and `writer migrate` moves its events to files (see *Versioning*).

## Notes: `notes/`

The writer's notes ([D12](https://github.com/heffrey78/gh-writer/issues/215)): ideas, what-ifs and questions kept with the novel. They aren't story facts, so they live outside `bible/`, and nothing that checks or compiles the story uses them. Each is one Markdown file in `notes/`, its name a slug that may change freely: front matter, then prose that may mention entries and events.

```markdown
---
id: note_4k8h2c
title: What if Ben never sold the plans?
tags: [ending, ben]
scenes: [sc_0d9wm4]
pinned: [sc_0d9wm4]
created: 2026-10-15
became: sc_0d9wm4
---
Then [Ada](#char_7f3k2q) has no reason to come home.
```

| Field | Required | Notes |
|---|---|---|
| `id` | yes | `note_` ID. |
| `title` | yes | |
| `tags` | no | Free-form strings. |
| `scenes` | no | Scene IDs: the scenes it belongs to, among whose notes the app shows it. |
| `pinned` | no | Scene IDs, of its `scenes`: where it's pinned to the top of the scene's notes. The app keeps one pinned note per scene. |
| `created` | no | When it was made: an ISO date, or date and time (`2026-10-15T14:03:09`, the writer's local time, as the app writes it). The app lists notes newest first. |
| `became` | no | The event or scene it was promoted to, when the note was kept. |

A note without `scenes` stands alone; one with them belongs to those scenes ([D12](https://github.com/heffrey78/gh-writer/issues/215), amended). A note is never mentioned itself. Tools from before notes leave `notes/` alone, which loses nothing, so notes came without a new format version.

## `diagrams/layouts.yaml`

Positions for hand-arranged diagrams, keyed by diagram name and then by record ID. Optional: a diagram without saved positions lays itself out. The app writes each position on one line, so moving a node changes one line. A position for an ID that isn't in the novel (an entry since deleted) is ignored, with the warning `W_LAYOUT_UNKNOWN`.

```yaml
layouts:
  relationship-graph:
    nodes:
      char_7f3k2q: { x: 120, y: 40 }
      char_b3n0vs: { x: 380, y: 60 }
```

## `images/`

Optional. Pictures of bible entries (their `image`), the book's cover (`cover` in `novel.yaml`) and pictures in the prose (`![…](/images/…)`), as ordinary files in git. Pictures in the prose are resized to at most 1600 px on their longest edge. The app names each from what it's for (`images/ada-varn.jpg`, `images/cover.jpg`, with `-2`, `-3`… if the name is taken) and resizes it before saving, so a picture is a few hundred kilobytes and every copy of the book stays quick to sync; the original isn't kept. A picture in the prose is named from its alt text (`images/a-map-of-varn.jpg`). Changing a picture replaces its file, and removing one deletes it once nothing else (another scene, an entry or the cover) shows it. GitHub refuses files over 100 MB, and so does the app.

## `compile.yaml`

Optional. How the manuscript is compiled to DOCX (standard manuscript format), EPUB and PDF: named presets, the first one the default. Without the file, Writer's own `manuscript` preset applies (every setting at its default).

The DOCX and the PDF are laid out as the book's kind says. The Novel's layout is standard manuscript format (the manuscript-format module's): chapters headed "Chapter Four: The Flood" and parts "Part One", a title page with the contact details and the word count rounded, from page 2 the running header Surname / SHORT TITLE / page, double-spaced, and "THE END" after the last chapter. A kind without it has the plain layout: each section headed by its title (or its level and number, "Month 2", when it has none, or when `chapter_heading` is `number`), parts by their level and number, a title page with the title, the byline and any `contact` lines, the word count only when `word_count` is `exact`, the page number alone at the top right, and one and a half spacing. `surname` and `short_title` are manuscript format's.

```yaml
presets:
  submission:
    title_page:
      author: J. Wikstrom              # default: novel.yaml's author
      contact: [J. Wikstrom, 1 Bridge Street, Varn, jw@example.com]   # top left of the title page
      surname: Wikstrom                # running header; default: the author's last word
      short_title: Varn                # running header; default: the title's first words
    scene_break: "#"                   # between scenes, and for a break within one
    chapter_heading: number-and-title  # or number ("Chapter Four"), or title
    word_count: rounded                # on the title page: rounded (default), exact or none
    front: [front/dedication.md]       # Markdown files before the chapters…
    back: [back/acknowledgements.md]   # …and after; a file's first heading is its title
  ebook:
    chapter_heading: title
    word_count: none
```

Only the story's words are compiled: a mention is its words, a link its text; front matter and hidden notes (HTML comments) are left out. A preset naming a file that isn't there is `E_MISSING_FILE`.

A scene's own headings, lists, tables and pictures (see *Prose conventions*) are set by every format:
- **Headings** go beneath the chapter's heading, in Word as headings 3–5.
- **Lists** keep their bullets or numbers (from their first number) and their nesting. Word numbers them with its own numbering.
- **Tables** are ruled, with their header row bold and repeated on each page in Word.
- **Pictures** are set as large as the page allows at their shape, centred, with their caption under them. In Word their alt text is the picture's description. The EPUB carries them under `pictures/`.

A picture whose file is missing, or isn't a JPEG or PNG, is left out (its caption stays), and the compiler says so.

The book's `cover` (in `novel.yaml`) is the EPUB's cover, shown first and by reading systems for the book, and the PDF's first page, before the title page; the manuscript's page numbers still count from the title page. Word manuscripts go out without one, as agents and editors expect. A cover that's missing or isn't a JPEG or PNG is left out, and the compiler says so. (A 16-bit or interlaced PNG is left off the PDF only: saved as a JPEG it works everywhere.)

Compile in the app (*Compile the manuscript…*), with `writer compile [dir] [--format docx,epub,pdf] [--preset <name>] [--from <chapter>] [--to <chapter>] [--out <dir>]`, or in a novel repository with `node .github/gh-writer/compile.mjs` (same options). Files are named for the book, and for the range when it isn't the whole book (`the-bridge-at-varn-chapters-1-2.epub`). Their dates are the latest commit's when everything in the novel is committed, otherwise now, so the same commit gives the same bytes on any machine. The command line writes to `compiled/` in the novel by default, a folder that ignores itself in git.

The novel template's *Compile* workflow compiles on demand (Actions → Compile → Run workflow, with a preset, range and formats; the files are kept with the run) and for every named checkpoint pushed (see Checkpoints).

## Story time

Story time is the story-time module's: a kind that doesn't use it has none, and its pieces' `when` is a key it doesn't know. A scene's or event's `when` places it in story time, and `duration` (ISO 8601, e.g. `PT45M`, `P3D`; a year counts as 365 days, a month as 30) gives its end.

- `at` is an ISO date or date-time, read as written (not in anyone's time zone).
- `day` (with an optional `time`, `HH:MM`) is a day of the story. With `calendar.start` in `novel.yaml`, day 1 is that date, day 0 the day before, and so on, so relative days and dates share one timeline. Without it, relative days are only ordered among themselves.
- Something without a `when` is undated.

In story-time order, dated items come first, then relative days without a calendar; reading order breaks ties. Two items overlap when one starts before the other ends (an item without a duration is a moment). A character in two overlapping items on the same scale, both with locations and none in common, is a `W_TIME_OVERLAP` warning; a scene's characters include its point of view.

## Diagram snapshots

`writer snapshots` (and the novel template's *Diagrams* workflow, on every push to the default branch) writes the novel's diagrams into `diagrams/` as files GitHub shows:

| File | What |
|---|---|
| `diagrams/README.md` | An overview: the relationship graph at the start and the end of the book and the timeline in Mermaid (which github.com draws), with every SVG embedded |
| `diagrams/relationships.svg` | The relationship graph at the end of the book, nodes where `layouts.yaml` places them |
| `diagrams/plotlines.svg` | Plotlines against scenes: major and minor beats, quiet stretches past `plotline_gap` shaded |
| `diagrams/presence-characters.svg`, `diagrams/presence-themes.svg` | Who and what is in each scene (the presence module's, for the types of the kind's fields marked for it) |
| `diagrams/timeline.svg` | The book in story time, joined to reading order |

They are generated from the same data as the app's views, say so at the top, and are the same bytes for the same novel, so they change only when the story does. Don't edit them; `layouts.yaml`, in the same folder, is the author's.

## `dictionary.txt`

Optional. Words the spell checker accepts in this novel, on top of its language dictionary: invented words, dialect, technical terms. Names and aliases from the story bible are accepted already, so they don't need listing.

```
# Words the spell checker accepts in this novel, one per line.
# Names and aliases from the story bible are accepted already.
ironwork
steamline
```

- One word per line. Blank lines and lines starting with `#` are ignored.
- Keep the words sorted (the app inserts new words in place), so adding a word is a one-line change that merges cleanly.
- Case matters as written: `Varn` accepts "Varn" (and "VARN"), while `varn` accepts any capitalisation.

The validator doesn't read this file.

## Checkpoints

A checkpoint is a named point in the novel's history to come back to, such as "Before the big cut". It's an annotated git tag named `checkpoint/<time>-<slug>`, where the time is UTC (`2026-10-05-183012`) and the slug comes from the name (`before-the-big-cut`). The tag message is the name on its first line, then trailers:

```
Before the big cut

Words: 81234
```

- `Words` is the manuscript's word count at the checkpoint.
- `Checkpoint: auto` marks one the app took itself, before a restore.
- `Version` is the branch (version) it was made in: the main version's branch, or `version/<slug>`. Checkpoints made before versions existed have none.

Tags sort by name in the order they were made: the app never gives a new checkpoint a time at or before the newest one's. Checkpoints are pushed with the branch, so every clone sees them, and the novel template's *Compile* workflow compiles each named one (not `auto`) to DOCX, EPUB and PDF, attached to a GitHub Release titled with its name. Restoring one brings back `manuscript/` and `bible/` as they were then, or one scene, found by its ID.

## Versions

An alternate version of the novel (a different ending, a cut subplot) is a git branch named `version/<slug>`, the slug made from the name the author gave it (`version/a-darker-ending`). The name itself is kept as the branch's description (`git config branch.version/<slug>.description`), which stays in the clone where it was made; elsewhere the slug stands in for it ("A darker ending"). The **main version** is the branch the novel lives on: the remote's default branch, else `main`, else `master`. Other branches are left alone.

Versions are pushed and fetched with sync, like the main version. Adopting one merges it into the main version (a merge commit "Adopt version “…”", or a fast-forward when the main version hasn't moved). Discarding one first tags its last commit as an automatic checkpoint ("Discarded version “…”"), then deletes the branch, and the next sync deletes it on the remote.

## Upgrading a novel's tools

The novel template vendors Writer's tools into `.github/gh-writer/` and runs them from `.github/workflows/`. A novel made from an older template doesn't get new ones by itself; copy them from the template and commit:

```sh
git clone --depth 1 https://github.com/heffrey78/writer /tmp/writer
cp -R /tmp/writer/templates/novel/.github/gh-writer/. .github/gh-writer/
cp /tmp/writer/templates/novel/.github/workflows/*.yml .github/workflows/
cp /tmp/writer/templates/novel/.gitattributes .
git add .github .gitattributes
git commit -m "Update Writer's tools"
```

`writer migrate` updates them as it moves a novel to a new format. The tools only read and write the novel's files, so updating them is safe at any time; `init.mjs` and the *Set up novel* workflow do nothing in a novel already set up. The compiler (`compile.mjs`, with its type in `fonts/`) and the *Compile* workflow came with the compile feature: copy both to compile on GitHub.

## Validation

`writer validate [dir]` (or `node .github/gh-writer/validate.mjs [dir]` in a novel repo) reports **errors**, which must be fixed, and **warnings**, which are advisory. It exits with status 1 if there are any errors.

### Errors

| Code | Meaning |
|---|---|
| `E_MISSING_FILE` | The book has no manifest (`book.yaml`, or `novel.yaml` in formats 1 and 2), or no `manuscript/_order.yaml`. |
| `E_PARSE` | A YAML file or front matter block cannot be parsed. |
| `E_SCHEMA` | A file breaks its schema: a required field is missing, or a value has the wrong type, enum value or ID format. Also used for a relationship type defined twice. |
| `E_SCHEMA_VERSION` | `schema_version` is newer than this validator supports, or `novel.yaml` says format 3, whose manifest is `book.yaml`. Nothing else is checked. |
| `E_UNKNOWN_KIND` | `book.yaml` names a kind of book this validator doesn't ship, or none. Nothing else is checked. |
| `E_ENTITY_TYPE` | A custom entity type reuses a reserved or existing key, prefix or folder (`events` is reserved), or a relationship type's `from_types` / `to_types` names an unknown entity type. |
| `E_UNKNOWN_FOLDER` | A folder under `bible/` contains Markdown files but doesn't belong to any entity type. Folders of other files, such as `bible/images/`, are fine. |
| `E_DUPLICATE_ID` | Two records share an ID. |
| `E_ID_PREFIX` | An ID's prefix doesn't match its record, e.g. a scene whose ID is not `sc_…`, or a character file in `bible/locations/`. |
| `E_DANGLING_REF` | A reference, including a mention link, names an ID that doesn't exist. |
| `E_REF_TYPE` | A reference names the wrong kind of record, e.g. a `pov` that isn't a character, a `since` that isn't a scene, a mention of something that's neither an entry nor an event, or a scene's `entities` listing a character (built-in types have their own fields). |
| `E_MISPLACED` | A file is somewhere the layout doesn't allow, e.g. a scene outside a chapter folder, or parts and chapters mixed at the top level. |
| `E_ORDER_MISSING` | A part, chapter or scene exists but isn't listed in its parent's order file. |
| `E_ORDER_UNKNOWN` | An order file lists an ID that isn't present in that folder. |
| `E_ORDER_DUPLICATE` | An order file lists the same ID twice. |
| `E_UNKNOWN_REL_TYPE` | A relationship's `type` isn't defined in `novel.yaml`. |
| `E_REL_ENDPOINT_TYPE` | A relationship's `from` or `to` entity type isn't allowed by its type's `from_types` / `to_types`. |
| `E_REL_RANGE` | A relationship's `until` isn't after its `since` in reading order. |

### Warnings

| Code | Meaning |
|---|---|
| `W_UNKNOWN_KEY` | A field this format doesn't define (probably a typo). |
| `W_FILENAME_ORDER` | A file or folder's `NN-` prefix disagrees with its position in the order file. |
| `W_HARD_WRAP` | A prose paragraph is split across lines without an intentional line break. |
| `W_POV_NOT_PRESENT` | A scene's `pov` character isn't in its `characters` list (the point-of-view module's check). |
| `W_REL_SELF` | A relationship's `from` and `to` are the same entity. |
| `W_LAYOUT_UNKNOWN` | `diagrams/layouts.yaml` places an ID that isn't in the novel. |
| `W_MISSING_IMAGE` | The cover, an entry's `image` or a picture in prose names a file that isn't in the repository. |
| `W_IMAGE_OUTSIDE` | A picture in prose isn't `/images/<name>`: its path is relative (github.com would look in the scene's own folder) or outside the novel. |
| `W_TIME_OVERLAP` | A character is in two scenes or events at different locations whose story times overlap (see *Story time*; the story-time module's check, which takes people and places from what their entry types are). |
| `W_NOTE_PIN` | A note is pinned in a scene that isn't one of its `scenes`. |
| `W_SIDEBAR_UNKNOWN` | `sidebar` in `book.yaml` names a group or a page the book's kind doesn't have. |
| `W_EVENTS_YAML` | A novel in format 2 still has events in `bible/events.yaml`: run `writer migrate` to give each a file of its own (the off-page-events module's check). |

## Versioning

`schema_version` increases only for changes that old tools would misread. Additive optional fields don't bump it. Tools refuse a novel in a newer format than theirs (`E_SCHEMA_VERSION`) rather than misread it, and read older ones. Machine-readable JSON Schemas for every file kind are in [`packages/core/schemas`](../../packages/core/schemas).

`writer convert [dir] --to journal` (or, in the app, *Make this book a journal…*) makes a journal kept as a novel a Journal, as one commit: every ID stays (the Journal's former prefixes are the Novel's), its folders, chapters, scenes and lists take the Journal's names, and an entry without a date is dated from its title. It refuses what a journal has no place for (a point of view, plotlines, off-page events) rather than drop it.

`writer migrate [dir]` moves a book to the newest format as one commit, and updates its tools in `.github/gh-writer/` to read it. The app moves a novel in format 1 to format 2, once you agree, the first time it changes an off-page event (which format 2 keeps differently), and to format 3 only when you ask (*Move this book to the new format…*): nothing a novel does needs it.

| Version | What changed |
|---|---|
| 3 | Books have kinds ([D15](https://github.com/heffrey78/writer/issues/11)): `book.yaml` replaces `novel.yaml`, with `kind` (`novel` for every book before it). gh-writer, and tools from before format 3, find no `novel.yaml` and refuse the book rather than misread it. Migrating renames `novel.yaml` to `book.yaml`, setting `schema_version: 3` and adding `kind: novel`. |
| 2 | Notes in `notes/` were added later without a new version: older tools ignore them, losing nothing ([D12](https://github.com/heffrey78/gh-writer/issues/215)). Off-page events are files of their own in `bible/events/`, with the note as prose and an optional `scene` ([D11](https://github.com/heffrey78/gh-writer/issues/206)). Mentions may name events. `events` is no longer a custom type's folder. Migrating writes each event in `bible/events.yaml` to a file and removes it. |
| 1 | The first format. |
